1. Executive Summary & Core Requirements
The Flash Sale & Inventory Engine is designed to handle extreme concurrency, prevent inventory overselling, and maintain sub-millisecond responsiveness during flash sale events.

Key Performance & Architectural Goals
Goal	Description
Prevent Overselling	Guarantee zero race conditions under thousands of concurrent checkout requests.
Database Offloading	Shield primary persistent storage (PostgreSQL) from write contention and high read IOPS.
Asynchronous Processing	Shift non-critical operations (order generation, notification, persistent state sync) to background workers.
Controlled User Experience	Implement a virtual queue with polling to control request flow and stabilize system throughput.

4. Operational Workflows & System Mechanics
A. Pre-Sale Warm-Up (Cache Pre-Warming)
To eliminate Cache Stampedes (Thundering Herd Problem) at sale launch:

Exactly 5 minutes prior to the sale start, a scheduled Celery Beat task queries PostgreSQL for active sale items.

Stock counters are populated into Redis keys (flash_sale:item:<id>:stock).

Keys are persisted for the duration of the sale without aggressive, unmanaged hard TTLs.

text
PostgreSQL (Source of Truth) ---> Celery Beat Job (T-5 min) ---> Redis (Live Counter)
B. High-Concurrency Stock Reservation Flow
User Request: User submits a purchase request via POST /api/v1/sale/reserve/.

Redis Execution: Django executes an Atomic Decrement (DECR) or Lua script directly in Redis memory.

Branching Logic:

If Counter ≥ 0: Reservation successful. A temporary reservation token with a 5-minute checkout window is generated.

If Counter < 0: Stock is exhausted. Request fails immediately with HTTP 409 Conflict or routes the user to the Virtual Waiting Line.

text
Client POST ---> Django ---> Redis DECR
                               |
                   +-----------+-----------+
                   |                       |
               Counter >= 0            Counter < 0
                   |                       |
            Reserve Success          Fail Fast / Queue
            (Issue Token)           (HTTP 409 / Wait)
C. Periodic Batch Flushing (Database Persistence)
To prevent slamming PostgreSQL with thousands of individual UPDATE queries per second, the engine utilizes a Periodic Batch Flush pattern:

Execution Interval: Every 5 seconds, Celery Beat executes a synchronization worker.

Aggregation: The worker reads active inventory numbers across all live Redis stock counters.

Bulk Write: The worker issues a single SQL CASE statement via Django's bulk_update() to update all modified PostgreSQL rows in a single database round-trip.

D. The 5-Minute Checkout Lifecycle & Reclaiming Unpaid Inventory
When stock is successfully reserved, an order record with status PENDING_PAYMENT and an expires_at timestamp (+5 minutes) is generated via background Celery task.

Expired Order Cleanup: A worker sweeps for PENDING_PAYMENT orders where expires_at < current_time.

Stock Re-injection: If an order expires unpaid:

PostgreSQL Order status updates to EXPIRED.

Redis atomic counter is incremented (INCR) by the returned quantity.

The newly available slot is assigned to the next user in the queue.

E. User Interface Interaction (Virtual Queue & Short Polling)
To prevent holding expensive persistent connections open (like WebSockets or Server-Sent Events) across tens of thousands of idle clients:

Upon joining a sale or waiting line, the client receives a unique Ticket ID.

The browser initiates Automated Short Polling every 3 seconds to GET /api/v1/queue/status/?ticket=<id>.

Django evaluates the ticket directly against Redis memory in ~2 ms, returning the user's status (WAITING, RESERVED_ELIGIBLE, or EXPIRED).

5. Summary Matrix of Architectural Decisions
Challenge	Adopted Solution	Primary Benefit
Overselling / Race Conditions	Atomic Redis operations (DECR / Lua)	Guarantees absolute sequential processing at single-thread speed.
Cache Stampede	Pre-warming cache 5 minutes prior	Zero read hits on PostgreSQL when sale goes live.
Database Overload	Periodic Batch Flushing via bulk_update()	Replaces 10,000 individual SQL queries with 1 grouped query.
Abandoned Shopping Carts	5-Minute Sliding Reservation + Expired Sweeper	Reclaims held stock automatically and returns it to live pool.
High Polling Traffic	Direct Redis Key Lookup (No DB IO)	High request throughput with minimal CPU overhead.
